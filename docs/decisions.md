## Step C: room groups, gateway runtime (2026-09-26)

**From the user**

1. A wall is opened or closed by a person on the panel, from a **Room linking** menu. (The portal control page can do it too; a sensor is later.)
2. What happens when a wall opens or closes is **set in the portal, in the group settings**, per wall.
3. A group is **deployed as one action**: its rooms first, then its combined rooms.

**Made while building**

| #    | Decision                                                                                                                                                                                                                                                                                                                                                         | Why                                                                                                                                                           |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C-1  | Open and close settings are per **wall** (divider), not per group. Four choices: **off**, **on**, **follow** (on if the space it came from was on, else off), **restore** (what that space was doing last time it was live). Defaults: opening = follow, closing = off                                                                                           | Matches the proposal the user confirmed; per wall is unambiguous because only one wall changes at a time                                                      |
| C-2  | The wall's setting applies to every **new space** the change creates: the combined room that goes live on open, and each room or smaller combined room that becomes active on close                                                                                                                                                                              | One rule for both directions, no special cases                                                                                                                |
| C-3  | New columns `RoomDivider.onOpen`, `onClose`, `open` (additive migration `20260926120000_divider_actions`). `open` is only the last state the gateway reported; the gateway owns the truth                                                                                                                                                                        | Working rule: gateway state survives restarts and works offline                                                                                               |
| C-4  | The protocol carries groups in `ConfigResponse.groups` and open walls in `HeartbeatRequest.dividers`. Both default to empty, so gateways in the field keep working and the config version is unchanged for a gateway with no groups                                                                                                                              | Protocol stays version 1; old fields (`combinations`) are still tolerated until step D                                                                        |
| C-5  | A group is only sent to a gateway when **all** its ordinary rooms run on it                                                                                                                                                                                                                                                                                      | Rooms in a group are controlled together                                                                                                                      |
| C-6  | Applying the migration to the shared database was **not** done by the build: the permission check refused it as a production deploy. It must be run by the user (`pnpm --filter @kestrel/db exec prisma migrate deploy`) before the release PR to `main`                                                                                                         | Previews and production share `kestrel-dev`                                                                                                                   |
| C-7  | A suspended room stops **commanding** its devices (panel, triggers, signal detect, auto-off and timers are all ignored) but keeps its device connections and polling open                                                                                                                                                                                        | Simple and safe for the devices that allow several connections. Devices that allow only one connection would need the suspended room to disconnect: not built |
| C-8  | Resuming a room drops what it believed it was doing (activity, overlays) but re-reads the devices, so if the displays are on it comes back "on" with no activity chosen. Then the wall's setting runs                                                                                                                                                            | Someone else drove the devices meanwhile                                                                                                                      |
| C-9  | Opening a wall is **refused** if the combined room it would create is not running on the gateway (log, and the panel greys the wall out as "not available"). Closing is always possible                                                                                                                                                                          | Otherwise the joined rooms would have nothing running them                                                                                                    |
| C-10 | What a suspended room was doing (for **restore**) is kept in memory only. After a gateway restart, restore falls back to off                                                                                                                                                                                                                                     | Not worth persisting device activity across restarts yet                                                                                                      |
| C-11 | The gateway no longer runs old-style combinations: `CombineCoordinator` and its tests are gone and it sends `combinations: []`. The old panel intent, bar, protocol fields and table are removed in step D                                                                                                                                                       | Keeps C reviewable; nothing in the field depends on them running                                                                                              |
| C-12 | A panel shows and controls **the room that is running its space**: itself, or the combined room while walls are open. Panel access (PIN, trusted IPs) and branding still come from the panel's own room                                                                                                                                                          | A person in Room A sees the combined room's controls with Room A's PIN rules                                                                                  |
| C-13 | The Room linking menu lists the walls that touch the space the panel controls (its own walls and the walls of whatever is joined to it), open or closed                                                                                                                                                                                                          | Lets someone in a joined space also close the far wall                                                                                                        |
| C-14 | No telemetry event for walls moving yet (a new event type would be rejected by an older cloud). Wall state reaches the cloud through the heartbeat                                                                                                                                                                                                               | Deploy order safety                                                                                                                                           |
| C-15 | The **Link rooms** button is on the top bar for every room in a group, **including the off screen**, and the portal control page and phone page get it for free (they render the same panel)                                                                                                                                                                     | Rooms are usually linked before the room is started                                                                                                           |
| C-16 | The menu speaks about **combining the rooms' AV systems**, not walls: "Combine with Room B" / "Linked with Room B" and Combine / Separate buttons, asking first. It lists one choice per neighbour (from the wall's rooms not already in the space). Walls are a dev-side idea (group editor only)                                                               | **User decision** (2026-09-26): the language transfers better for the people in the room                                                                      |
| C-17 | Moving a wall from the portal or a phone is always written to the activity log (`wall.set`), unlike volume nudges                                                                                                                                                                                                                                                | It affects several rooms                                                                                                                                      |
| C-18 | The group editor shows "Open now" against a wall the gateway last reported open                                                                                                                                                                                                                                                                                  | Lets a dev see the rooms are joined                                                                                                                           |
| C-19 | **Deploy group** is all or nothing on checks: every room and combined room must have a valid design, a gateway (the same one) and every combined room must exist, otherwise nothing is deployed and every problem is listed. A release is published only where the design changed since the latest release; a room already running its latest release is skipped | One action must not leave a group half deployed                                                                                                               |
| C-20 | Rooms are deployed in order (members, then combined rooms) but the gateway applies them together on its next sync; there is no gateway-side ordering                                                                                                                                                                                                             | Combined rooms do not need their members' releases to load                                                                                                    |
| C-21 | Publishing was moved out of the release router into `release-service.ts` (no behaviour change) so one room and a whole group publish the same way                                                                                                                                                                                                                | Avoid two copies of the publish rules                                                                                                                         |
| C-22 | The wall logic moved from the gateway into the engine (`GroupController`) so the browser simulator runs the same code. The gateway keeps a thin `GroupCoordinator` that saves the open walls                                                                                                                                                                     | One implementation to test                                                                                                                                    |
| C-23 | The **group simulator** gives every room its own simulated equipment (they do not share devices), one panel that stands in a chosen room, and plug/unplug for the laptops of the room that is running. Custom-driver quick actions are not shown (as in the room simulator)                                                                                      | Enough to try linking and separating; shared physical devices are not modelled                                                                                |

## Step E: audit retention and export (2026-09-26)

Retention default and long-kept events were the two open questions in the staff plan; both were decided while building.

| #   | Decision                                                                                                                                                                                                                                                                                                                                           | Why                                                                                                                              |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| E-1 | The activity log is kept **12 months** by default                                                                                                                                                                                                                                                                                                  | The proposal in the staff plan review                                                                                            |
| E-2 | Only **staff (admin)** change an organisation's period, with a reason: at least 12 months, at most 10 years. Customers cannot shorten it. The change is written to the organisation's own log and to the staff trail                                                                                                                               | An audit trail the audited party can shorten is not a trail                                                                      |
| E-3 | **Billing and access-change events are kept 7 years** (or the organisation's period if longer): actions starting `billing.`, `license.`, `member.`, `invite.`, `msp.`, `session.`, `staff.`, `org.staff_access`, `org.retention`, `marketplace.checkout`                                                                                           | Money and who-could-get-in are what disputes and audits ask about                                                                |
| E-4 | The **staff trail** (who at Kestrel looked at what) is kept 7 years                                                                                                                                                                                                                                                                                | It records staff access to customer data                                                                                         |
| E-5 | The period lives in a **new table** `OrgRetention` (one row per organisation that differs), not a column on `Org`                                                                                                                                                                                                                                  | A new column on `Org` would break every organisation query until the migration is applied; a new table only affects what uses it |
| E-6 | **Export**: owners download their own log; staff (support or admin) download any organisation's. CSV or JSON, whole log or a date range, capped at 50,000 rows with a warning. Every download is itself logged (in the organisation's log, or the staff trail)                                                                                     | Exports are as sensitive as reading the log                                                                                      |
| E-7 | CSV cells that start with `=`, `+`, `-` or `@` are prefixed so a spreadsheet does not run them as formulas; downloads include a UTF-8 marker so Excel reads accents                                                                                                                                                                                | A person's name in the log must not become a formula                                                                             |
| E-8 | The daily job prunes the activity log **separately** from the telemetry clean-up and reports its own failure in the response                                                                                                                                                                                                                       | A problem with one must not stop the other                                                                                       |
| E-9 | The migration `20260926140000_org_retention` was **not applied** by the build (the permission check refuses changes to the shared database). Run `pnpm --filter @kestrel/db exec prisma migrate deploy` before the release to `main`. The staff end-to-end script (`apps/web/scripts/e2e-staff-msp.mts`) needs the dev database, so it was not run | Same as C-6                                                                                                                      |

## Step K: SLA targets on tickets (2026-09-26)

Planned "after the first customers"; built early because it needs no new data (everything is worked out from times a ticket already has), so it cannot go wrong for anyone until they look at it.

| #   | Decision                                                                                                                                                                                                                                                                                                                                                             | Why                                                                                                                     |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| K-1 | Targets by priority, in **calendar time** (nights and weekends count): **urgent** reply 1 h, resolve 4 h; **high** 4 h / 1 day; **normal** 1 day / 5 days; **low** 3 days / 10 days. Fixed in code (`packages/model/src/sla.ts`), not per organisation                                                                                                               | Simple, visible defaults; business-hours calendars and per-organisation targets need a timezone and holiday model first |
| K-2 | Nothing is stored. The state (ok, due soon, overdue, met, met late) is worked out when a list or ticket is read. **Due soon** means 25% of the time or less is left                                                                                                                                                                                                  | No migration, cannot drift from the data                                                                                |
| K-3 | The clock: for a ticket **with Kestrel** it starts at the escalation and only a Kestrel reply answers it; otherwise it starts when the ticket was raised and any public reply from someone other than the requester answers it. For a ticket sent to a provider this uses the creation time, which is only approximate if it was sent later (no "sent at" is stored) | Matches who is expected to act                                                                                          |
| K-4 | A ticket closed with no reply counts as answered when it was closed. Internal notes never answer a ticket                                                                                                                                                                                                                                                            | Matches what the customer saw                                                                                           |
| K-5 | Shown as words with colour ("Reply due in 2 h", "Resolve overdue by 1 d", "Resolved in time") in the staff queue and ticket, the provider queue, and the organisation's ticket list and page. **Hidden from customer viewers**                                                                                                                                       | Targets are for the people working requests                                                                             |
| K-6 | Queues put overdue before due soon before the rest **within a priority**                                                                                                                                                                                                                                                                                             | Priority stays the main order                                                                                           |
| K-7 | **Not built:** warnings by email or Teams as a target nears (the badge is the warning), pausing the clock while waiting for the customer, and reports of how often targets were met                                                                                                                                                                                  | Needs the business-hours and status decisions above                                                                     |

### Slice 2: bindings and credentials (2026-09-26)

| #    | Decision                                                                                                                                                                                                                                                       | Why                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| DS-1 | A room has one **binding set** (`RoomBinding`): addresses in plain JSON, logins sealed with `KESTREL_SECRETS_KEY`, plus a per-device pointer to a **credential set**. Its `version` goes up on every change, including a change to a credential set the room uses | An IP change or password rotation needs no new release                                |
| DS-2 | A device's values are layered: credential set (lowest), then the device's own addresses, then its own logins. **Bindings win over anything still inline in the design**                                                                                       | Old rooms keep working; the editor cannot silently override the Setup tab             |
| DS-3 | **Old rooms migrate on publish.** Publishing moves inline addresses and logins into the binding set (only filling what it lacks). Without a secrets key, logins stay inline and only addresses move                                                            | No manual step, and nothing is lost if the key is missing                             |
| DS-4 | A release keeps its addresses apart (`bindingsExternal`) **only when its gateway has said it can fetch them** (`features: ["bindings"]` in the heartbeat). Otherwise the release carries the merged values, as before                                              | An older gateway would have no address. Deploy order is safe in both directions       |
| DS-5 | A gateway fetches `GET /rooms/:id/bindings`, signed like a manifest (same key, hash of canonical JSON). It checks the signature, the room, the organisation and that the version is at least the one assigned. It saves the raw signed copy and re-verifies it on every boot | A tampered file on disk or a forged response is refused                               |
| DS-6 | A **changed binding with no new release** restarts the room the careful way (build alongside, wait for devices, swap). If the new address is dead the room keeps running on the old one and reports "New addresses rejected". Only a newer version retries      | Same safety as a deployment                                                           |
| DS-7 | Logins are **write-only in the browser**: the view says "set" or "not set", never the value. Audit entries name the fields changed, never values                                                                                                               | Credentials must not be readable after entry                                          |
| DS-8 | Deploy is **blocked until every required binding is set** ("Needs setup"), for a single room, a group deploy and a room moved to a new gateway. Publishing without deploying is still allowed                                                                   | Docs: the validator blocks deploy until required bindings are set                     |
| DS-9 | **Templates carry no addresses or logins.** Save as template, clone, starter templates and creating a room from a template all strip them, using each driver's own setting scopes (custom drivers included)                                                    | DC-5                                                                                  |
| DS-10 | **Test connection** reuses the existing allowlisted `test_device` command, so it tests what the room is **running now**: save, wait for the gateway to apply it (about a minute), then test. It needs the room to be on a gateway                              | No new command in an old gateway. A pre-deploy test would need a new command          |
| DS-11 | Gateways keep the signed bindings in their local SQLite file **unencrypted** (as the credential already is). Sealing to each gateway's own key is DC-12, a later slice                                                                                          | Same trust as today; the cloud database is sealed                                     |
| DS-12 | The **generic TCP** port is now a required binding; other generic protocols leave it optional                                                                                                                                                                  | A TCP device with no port cannot connect                                              |
| DS-13 | A gateway **reports the bindings version** it runs (`RoomReport.bindingsVersion`, stored as `Room.reportedBindingsVersion`). The Setup tab shows a note while it differs from the saved version. It is not yet part of the room's sync state                    | Enough to see it; a "binding pending" state can join drift detection later            |
| DS-14 | **Not built:** the credential-set picker for a whole site, per-slot non-secret defaults (a template does not remember port 4352), duplicate room, and the bulk grid (slice 3)                                                                                    | Later slices                                                                          |
